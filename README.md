# האנגר (HANGAR)

מערכת קטלוג אמל״ח ודרישות/טיקטים, כלל-זרועית. שני חלקים נפרדים:

- **`client/`** — האתר (Vite + React), מדובר ל-GitHub Pages.
- **`data/`** — ה-API האמיתי (Express) + "מסד הנתונים" (קבצי JSON). רץ מקומית תמיד; ניתן גם לאירוח ציבורי (Render, ראו למטה) כדי שמצב הפיתוח/QA יעבוד גם בקישור הציבורי, לא רק אצלך.

## הרצה מקומית (צריך Node.js גרסה 20 ומעלה)

הכי פשוט — הרצת שני התהליכים ביחד מהשורש:

```bash
npm run install:all   # מתקין תלויות גם ב-client וגם ב-data, פעם אחת
npm run dev           # מריץ את שניהם יחד
```

הטרמינל יראה כתובת כמו `http://localhost:5173/commando/` — פותחים אותה בכרום.
כל שינוי בקוד (בשני החלקים) ישתקף מיידית, בלי לרענן ידנית.

לחלופין, כל תהליך בנפרד (שני טרמינלים):

```bash
npm run dev --prefix client   # הלקוח, פורט 5173
npm run dev --prefix data     # ה-API, פורט 4000
```

### הגדרת `data/.env`

`data/` צריך קובץ `.env` מקומי (לא ב-git — ראו `data/.env.example`). בהרצה ראשונה:

```bash
cp data/.env.example data/.env
```

ואז מגדירים `ADMIN_SECRET` לערך אמיתי משלכם — זה הסוד שפותח את מסך ניהול משתמשי הפיתוח/הערות ה-QA (ראו "מצב פיתוח" למטה). שאר הערכים ב-`.env.example` כבר טובים לפיתוח מקומי.

### משתמש-פיתוח לדוגמה

**עדכון 2026-09-02: המשתמש הזרוע הזה כבר לא קיים בפועל** — `data/config/dev-users.json` הנוכחי מחזיק רק משתמשי-פיתוח אמיתיים שנוצרו דרך מסך הניהול (לא סיסמה ידועה לאף אחד מהם, רק hash). זה תועד כאן בטעות במשך זמן ולא עודכן — ראו `FORCLAUDE.md`'s "Testing / verification workflow" section למתכון עדכני ליצירת משתמש-פיתוח זמני לבדיקה מקומית.

```

  theme.js         — טוקנים + CSS גלובלי
  screens/         — מסכי האפליקציה (קטלוג, דרישות, הרשאות, ניהול מערכת...)
  components/      — רכיבים משותפים (אמבלמה, גלריה, חיפוש, עימוד...)
  api-client/      — כל קריאות ה-API (http.js הוא ה-wrapper המשותף)
  devtools/        — כל מה שקשור למצב פיתוח/QA (לא חלק מהמוצר האמיתי)

data/
  server.js        — נקודת הכניסה של Express
  routes/          — כל endpoint
  middleware/       — אימות, הגבלת קצב, טיפול שגיאות
  lib/             — קריאה/כתיבה ל-JSON, סשנים, סיסמאות
  mock/            — דאטהסט הדגמה (git-tracked, זרע קבוע)
  db/              — דאטה אמיתי/live (לא ב-git, ריק כברירת מחדל — לא שורד אירוח בחינם, ראו למטה)
  config/          — dev-users.json (משתמשי פיתוח, git-tracked) + data-mode.json (מצב נוכחי, לא ב-git)
  annotations/notes/ — קובץ אחד לכל הערת QA (git-tracked)
```

## מצב פיתוח (DEV) ו-overlay ה-QA

לחיצה על הכפתור הנעול "DEV" (פינה ימנית-תחתונה) פותחת טופס התחברות. אחרי התחברות מוצג:
- **בורר תפקיד/חטיבה/זהות** — בדיוק כמו קודם, סימולציית תפקיד ללא SSO אמיתי.
- **מתג נתוני הדגמה / מערכת ריקה** — עובר בין דאטהסט קבוע (mock) לדאטה אמיתי שנשמר לדיסק (live).
- **תצפית Dev (עין)** — הדלקה/כיבוי של הילה מוארת שעוקבת אחר העכבר; **Ctrl/Cmd+קליק** על כל חלק במסך פותח תיבת הערה — נשלחת לתור הערות ה-QA.
- **⚙ ניהול** — גישה נפרדת (סוד מנהל) לניהול משתמשי הפיתוח וסקירת/ייצוא הערות ה-QA.

## שמירת מרשם המשתמשים והערות ה-QA — דרך Git, לא מסד נתונים

בכוונה אין כאן מסד נתונים אמיתי: `data/config/dev-users.json` ותיקיית
`data/annotations/notes/` הן מקור האמת, ו-`data/lib/githubPersist.js` הוא
מה שמסנכרן אליהן — כל שינוי (הוספת משתמש-פיתוח, הערת QA חדשה, סימון
"טופל") נכתב גם לדיסק המקומי וגם נשלח כ-commit ישירות ל-repo (דרך ה-API
של GitHub), ובעליית השרת המקומי/המרוחק תמיד "נשלף" קודם המצב העדכני
מ-git. ככה גם אירוח בחינם עם דיסק זמני (כמו Render free tier, שמאפס את
הדיסק המקומי בכל spin-down/redeploy) לא מאבד כלום — וכ"בונוס", היסטוריית
ה-git *היא* יומן השינויים.

כדי להפעיל את זה: `GITHUB_TOKEN` ב-`data/.env` — Personal Access Token
מסוג fine-grained, מוגבל **רק** לריפו הזה, עם הרשאת Contents: Read and
write (ליצור: https://github.com/settings/personal-access-tokens). בלי
טוקן — הכול ממשיך לעבוד בדיוק כמו היום, רק מקומית בלבד (הדיסק המקומי לא
מתאפס בעצמו, אז זה לא בעיה בפיתוח).

## אירוח ציבורי (Render)

`render.yaml` בשורש הריפו מגדיר Blueprint ל-Render (שכבת החינם מספיקה —
ראו למעלה למה):

1. ב-Render: **New → Blueprint**, מחברים את הריפו הזה.
2. אחרי היצירה, ב-Environment של השירות `hangar-data`: מגדירים
   `ADMIN_SECRET` (סוד אמיתי משלכם) ו-`GITHUB_TOKEN` (הטוקן שיצרתם למעלה).
3. אחרי הפריסה הראשונה, מעדכנים ב-GitHub: Settings → Secrets and
   variables → Actions → **Variables** → `VITE_API_BASE_URL` = הכתובת
   הציבורית של השירות + `/api` (למשל `https://hangar-data.onrender.com/api`),
   ואז מריצים מחדש את ה-workflow (או דוחפים קומיט) כדי שהאתר הבנוי יידע
   לאן לפנות.
